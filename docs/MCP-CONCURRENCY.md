# 共享 MCP 并发连接

## 0.1.4 的断开原因

官方 TypeScript SDK 1.32.2 在 `initialize` 和 `notifications/initialized` 完成后，会在后台发送 GET `/mcp` 探测事件流；应用随后调用 `listTools()`，产生另一个 POST。这两个请求会重叠，因此 20 个客户端的握手阶段可产生约 40 个同时在途的 HTTP 请求。

原服务同时处理最多 32 个 TCP 连接，但在 `accept()` 新连接后才检查容量。满载时直接丢弃刚接受的 socket，没有发送 HTTP 响应。客户端因此可能报告 `UND_ERR_SOCKET: other side closed`，工具列表请求失败。事件流 GET 的失败也可能只通过 SDK 的 `onerror` 通知，未使前台调用失败。

诊断对照：16 个客户端、峰值 32 个在途请求通过；20 个客户端、峰值 40 个在途请求可复现 GET 和 `tools/list` 连接关闭。仅在诊断中移除后台 GET 后，20 个客户端通过。最终回归和验收均保留完整 GET，未通过去除探测、添加重试或错峰连接隐藏问题。

真实 TCP 回归以 `100 Continue` 确认 32 个连接都已进入服务端并等待请求体，然后发起第 33 个合法请求。旧实现直接返回 EOF；这一场景不涉及 SDK 连接池，也没有等待到请求超时。

## 0.1.5 的处理方式

仅在活动连接数小于 32 时调用 `accept()`。短时突发连接先留在操作系统的有界监听队列里，等一个活动连接完成后再接受和处理。保持单个监听器、32 个活动连接、请求大小和超时限制；关闭应用仍会取消活动请求并释放端口。

该机制处理短时握手突发，不承诺无限并发。系统监听队列和客户端超时仍有边界；持续超载或大量停滞客户端可能造成等待。

## 回归与复核

```powershell
cargo test -p daynote-app http::tests::connection_burst_waits_for_capacity_instead_of_resetting_clients --locked
node scripts/verify-sdk-mcp.mjs http://127.0.0.1:47821/mcp "<设置页中的令牌文件路径>" 0.1.5
```

TCP 测试验证：满载时第 33 个请求保持等待；释放一个活动连接后，该请求在原 socket 上收到 200，不需要重试；停服能及时返回并重新绑定端口。

SDK 脚本固定使用 `package-lock.json` 中的官方 SDK，默认运行 10 轮，每轮同时启动 20 个客户端，完成握手、列工具和读取摘要，然后全部关闭再开始下一轮。它等待全部前台调用和后台请求收束，同时检查 `onerror`；20 个 GET 必须全部得到正常的 405 响应。任何连接关闭、请求超时或后台错误都会失败，不会提前关闭其他客户端而制造次生报错。

脚本只读取真实数据，不调用模型、不启动 CLI、不输出令牌或任务内容。Windows 安装器 CI 会对实际安装后的程序运行同一脚本。
